# 文件编辑引擎重设计（字符跨度匹配）

> 对应实现：`Services/DiffApplier.cs`、`Services/FileSystemService.cs`、`Services/Functions/FunctionRegistry.cs`（`modify_system_file` 描述）
> 回归用例：`Athena.Archive.Tests/Program.cs` 中 `diff: *` 与 `filesystem: chunked reads *`

## 0. 结论先行

`modify_system_file` 原本按**整行**匹配 SEARCH。对人写的源码没问题，但对机器生成的单行文件（压缩 JSON、minified 资源）等于不可编辑——那类文件整个文件就是一行，按行匹配意味着必须一字不差复述上万字符。

本次把匹配单位改成**字符跨度**：整行编辑只是起止恰好落在行边界的特例，行内片段成为一等公民。同时补上失败诊断、修掉一条静默写坏文件的解析路径、修掉分块读取切断 UTF-8 字符的缺陷。

---

## 1. 取证

### 1.1 事故现场（来自 `AthenaData/Logs/logs.db`）

日志库覆盖 2026-07-23 至 2026-08-13，共 21301 条。检索到两条匹配失败记录，时间戳 `2026-08-13T00:29:44` 与 `00:29:52`，相隔 8 秒。

目标文件 `~/Downloads/ability_demo.json`——**单行 JSON，10854 字节，全文只有 1 行、9690 字符**（spreadsheet skill 的输入文件）。两次 SEARCH 分别是：

```
尝试 1：{"formula":"SUM(G2:G13)","style":"integer-formula"}]},{"name":"预研预算"
尝试 2："integer-formula"}]},
```

两个都是那一行的**片段**。紧随其后的日志是 `python3 -c "...print(repr(s[i-40:i+40]))"` 和 `search_in_file`——模型在自证文本确实存在，最后绕道 python 完成修改。

**定性**：不是长行匹配缺陷，是匹配单位与文件形态不匹配。模型的取证（python 子串查找、`search_in_file` 的 `regex.IsMatch(lines[i])`）都是**子串**级判断，而 `modify` 要求**整行**相等——"证据成立"与"匹配失败"完全可以并存。

**唯一性核验**：`"integer-formula"` 在该文件中出现 **1 次**，因此两个 SEARCH 在全文都唯一。按字符跨度匹配，两次都应一次命中、无歧义。

### 1.2 语料测量（本仓库）

| 类型 | 行数 | 最长行 | >2000 字符的行 |
|---|---|---|---|
| `.cs` | 82410 | 974 | 0 |
| `.axaml` | 12132 | 1555 | 0 |
| `.md` | 156391 | 4892 | 2 |
| `.json` | 319157 | 3350060 | 14 |

人写的文件从不触发该问题；触发它的全部是机器生成的 JSON（`obj/project.packagespec.json`、`node_modules` 的各类 metafile、playwright 的 `help.json`、以及 skill 的输入输出文件）。

### 1.3 真实用量（3 周）

`read_system_file` 37 次 : `write_system_file` 7 次 : `modify_system_file` 4 次；`execute_terminal_command` 62 次（逐条核对，几乎全是 git / grep / find / dotnet build 的只读侦察，日常并未绕过文件工具）。

4 次 modify 中：2 次成功（AXAML 多块编辑，2 块与 5 块，均 Exact 一次命中）、1 次被配置文件自我保护拦下、1 次即上述事故。

### 1.4 代码级复现的另外两个缺陷

**分隔符劫持（静默写坏文件）**。标记识别原本用 `Trim().StartsWith("=======")`，文件中任何以 7 个及以上等号开头的行都会冒充分隔符。实测输入：

```
<<<<<<< SEARCH
标题
==========
正文
=======
新标题
==========
新正文
>>>>>>> REPLACE
```

解析成 `SEARCH=[标题]`、`REPLACE=[正文, =======, 新标题, ==========, 新正文]`，**报告成功**并把文件写成垃圾。触发面包括 markdown setext 标题下划线、纯等号分隔条、以及编辑带未解决冲突标记的文件。

**分块读取切断字符与行**。`ReadFileAsync` 按 50KB 字节硬切并 `Encoding.UTF8.GetString(buffer, 0, read)`。实测：边界落在汉字中间时 chunk#0 尾部产生 1 个 `U+FFFD`、chunk#1 头部 2 个；一条 9998 字节的长行被切成两半，chunk#1 的首行是真实行的子串——模型拿它当完整行去构造 SEARCH，必然失败。

### 1.5 失败诊断的结构性缺失

`NearestHint` 按**整行**相似度打分、阈值 0.5。当 SEARCH 只有一行时 `eq/m` 只能是 0 或 1，而 1 意味着 Trim 后相等——那在 Trimmed 层就已命中，根本走不到诊断。因此在默认 `fuzzyMatch=true` 下，**单行 SEARCH 失败永远返回 `null`**。这正是模型两次盲目失败后放弃的直接原因。

## 2. 设计

保留 `modify_system_file` 的名字与 SEARCH/REPLACE 外形（日志证明这个交互形状在 AXAML 多块编辑上一次命中，换掉纯亏），**换掉引擎与失败契约**。

### 2.1 匹配：四层降级

文件规范化成 `\n` 后视为字符序列，编辑 = 替换一段唯一确定的字符区间。

| 层级 | 语义 |
|---|---|
| `Exact` | 整行对齐 + 逐字符相等 |
| `TrailingWhitespace` | 整行对齐 + 容忍行尾空白 |
| `Trimmed` | 整行对齐 + 容忍首尾空白，命中后对 REPLACE 重缩进 |
| `Span` | 任意位置逐字符相等（行内片段） |

命中即停。前三层语义与行时代完全一致；`Span` 只在前三层全部落空时兜底。

**为什么 `Span` 必须排在最后**：若排在容错层之前，一个存在缩进漂移的整行 SEARCH 会优先命中别处的行内子串，比原来更糟。

**整行护栏**：`Span` 层拒绝"跨度两侧到行首/行尾之间只剩空白"的候选——那类目标属于第 2/3 层，落到 `Span` 会把整行编辑悄悄降级成半行编辑，留下孤立的缩进或行尾空白。有了这条护栏，`fuzzyMatch=false` 拒绝空白漂移等旧行为逐条保持不变。

实现上，整行对齐扫描全程用 `ReadOnlySpan<char>` 比较（`TrimEnd()` / `Trim()` 在 span 上无分配），只维护一个 `int[]` 行起点表，不再为每行每层生成规范化字符串。

### 2.2 唯一性与删除语义

- 唯一性按**全文出现次数**统计（同一行内出现两次也算冲突），冲突时报出每处的 `行L 列C` 加前后各 40 字符上下文，或要求 `replaceAll=true`。
- 多块**顺序**应用于工作副本，后一块在前一块的结果上搜索——因此跨块跨度重叠在结构上不可能发生，无需额外检测。任一块失败即整体放弃，不产出任何内容。
- 空 REPLACE 表示删除。整行命中时连同行尾换行一并吃掉，否则会留下空行（保持行时代 `RemoveRange` 的语义）。

### 2.3 失败诊断

- **0 命中**：二分求出 SEARCH 能够定位到的最长前缀（`O(log m)` 次 `IndexOf`），报告其位置、出现次数，以及第一个分歧字符处的"SEARCH 期望 / 文件实际"。
- **SEARCH 整体存在却未进入任何层**：只可能是被整行护栏挡下的严格模式，直接提示"与该行只差首尾空白，请设 `fuzzyMatch=true`"。
- **N 命中**：全部位置的 `行L 列C` 与上下文。

### 2.4 成功回执

`RegionPreview` 双形态：短行走行预览（`N | 内容`，与 `read_system_file` 同格式）；落点所在行超过 400 字符或落在行中部时改用**字符窗口**（前后各 40 字符 + `⟦替换内容⟧`）——在单行 9600 字符的文件上，"前后各两行"等于把整个文件回吐给模型。

### 2.5 解析层

标记按 **Trim 后完全相等**识别，不再用 `StartsWith`。劫持面从"≥7 个等号"收窄到"恰好 7 个等号"（SEARCH/REPLACE 格式的固有边界，无法完全消除）。

### 2.6 读侧协同

- 块边界向前对齐到 UTF-8 字符首字节：边界处的半个字符完整归属后一块，块与块严丝合缝，不丢内容也不重复。
- 块起点落在行中部时标注 `[本块自第 N 行第 M 个字符处开始，该行前半部分在上一块]`；块尾截断时标注 `[第 N 行在此截断，后续内容在下一块]`。

### 2.7 明确不做

`dryRun`、相似度/编辑距离模糊匹配、AST 结构化编辑、行号定位——均无证据支撑，且后两者会引入改错风险。

## 3. 验收

### 3.1 事故回放

按日志还原修复前的 `ability_demo.json`（1 行 9689 字符），把两个历史 SEARCH 原样喂入：

```
[尝试 #1] SEARCH 68 字符  → success=True tier=Span  落点 第 1 行第 7998 列
[尝试 #2] SEARCH 21 字符  → success=True tier=Span  落点 第 1 行第 8031 列
```

均一次命中且唯一。

### 3.2 回归用例

`Athena.Archive.Tests` 的 `diff:` 用例从 9 个扩到 18 个，另加 1 个分块读取用例：

- 历史成功的两块 AXAML 编辑仍在 `Exact` 层命中
- 两个历史失败的行内片段现在一次命中
- setext 下划线不再劫持分隔符（从"静默成功改坏"变成正确应用）
- 整行 SEARCH 不因行内偶然子串而产生歧义
- 空 REPLACE 删除整行、不留空行
- 单行 SEARCH 失败必定给出分歧位置
- 超长行编辑的预览是有界字符窗口
- 分块边界不产生 `U+FFFD`，两块拼接严格等于原文

### 3.3 性能（350KB / 6850 行真实源文件，端到端）

旧管线含 `FileSystemService` 侧的 Split/Join 固定开销（0.286 ms / 1612 KB），一并计入：

| | 耗时 | 分配 |
|---|---|---|
| 旧 · 命中 | 0.356 ms | 1721 KB |
| 新 · 命中 | 0.413 ms | 868 KB |
| 旧 · 未命中 | 0.916 ms | 4923 KB |
| 新 · 未命中 | 0.896 ms | 94 KB |

命中路径挂钟时间慢约 16%、分配减半；未命中路径耗时持平、垃圾降到 1/52。均在亚毫秒级，属卫生指标而非性能收益——真正的收益在能力（长行可编辑）与可恢复性（失败可自救）。

> 实现注意：单跨度走三段 `string.Concat`，不要走 `StringBuilder`——后者会先复制一遍原文再 `ToString` 复制一遍，在大文件上分配直接翻倍（首版实测 1552 KB / 0.639 ms，比旧引擎还差）。

## 4. 证据强度说明

| 结论 | 证据 |
|---|---|
| 整行匹配导致长行不可编辑 | 日志原文 + 唯一性核验 + 代码级复现 |
| 单行 SEARCH 失败零诊断 | 代码结构证明 + 复现 |
| 分隔符劫持静默写坏文件 | 代码级复现（无事故样本） |
| 分块读取产生 `U+FFFD` 与半行 | 代码级复现（无事故样本） |

事故样本为 **n=1**（3 周内 4 次 modify 调用中的 1 次）。机制已证实，**发生频率未测量**。若需频率证据，最低成本是补结构化失败日志（命中层级、SEARCH 长度、是否为某行子串、最长可匹配前缀长度）后持续观察。
