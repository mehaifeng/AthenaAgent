# Model metadata

These rules cover `Services/ModelMetadata/` and `Services/ModelCatalogService.cs`.

模型元数据的分层解析 —— `ModelIdentityMatcher`（外部模型 ID → OpenRouter 记录）、`OpenRouterModelMetadataCatalog` / `OpenRouterModelMetadataStore`（带 ETag 的增量快照）、`ProviderReportedMetadataParser`（供应商自报字段）、`ModelMetadataResolver`（按 `MetadataValueSource` 的优先级合成 `ResolvedModelMetadata`）。优先级是 **UserOverride > ProviderReported > Pinned/AutomaticOpenRouter > ApplicationDefault**。中间那一层是供应商自己在 `/v1/models` 里报的：OpenAI 协议只要求 id/object/created/owned_by，但聚合端点普遍多报 `context_length` / `max_completion_tokens` / `architecture` / `supported_endpoint_types`（OrcaRouter 实测 196 个模型：153 个带窗口、162 个带模态、76 个把 `openai-response` 单列为独立门面）。它压过 OpenRouter 两层，是因为它来自实际承接请求的那一家，而 OpenRouter 那一层是拿模型 ID 去猜同一个模型——带服务商前缀的聚合 ID 尤其容易猜歪。四条规则各有断言：自报里**没有任何能力数组**（`supported_parameters` / `tokenizer` / `canonical_slug` 在 196 条里出现 0 次），所以工具、推理、结构化输出三项仍旧只能由 OpenRouter 层回答，这一层绝不给它们署名；`supported_endpoint_types` 里**没有** `openai-response` 并不等于不支持（通道别名会漏报），因此它只在「报了」时发言，否则让位——抢答一个 Unknown 会把本可以回答「支持」的 OpenRouter 层挡在后面；`architecture.output_modalities` 会是 **`null`** 而不是缺键或空数组（196 条里 43 条），解析器必须显式区分，否则崩掉一半目录；`created` 是常量占位（191 条都是 `1626777600`），不要拿它排序或判新旧。取数路径也因此改了：`ModelCatalogService` 主路径直接读原始 JSON，SDK 的 `OpenAIModelClient` 只保留协议规定的那几个字段、会把上面这些全部丢掉；SDK 仅作回退（它带着重试策略），此时结果的 `Reported` 为 `null`，而 **`null` 与空字典含义不同**——`null` 表示这一轮没读到，已有自报值原样保留；空字典才是端点确实没报、该清掉过期值。搞反的代价是一次网络抖动把整个库存的窗口打回应用默认值，而那是用户最不会主动去看的地方。这条取数路径的**超时跟随 `AppConfig.Timeout`**（仍由 `OpenAiClientOptionsFactory.NormalizeTimeoutSeconds` 夹取），不是目录服务自己的常量：它和对话走的是同一条链路、同一个端点，一个更短的独立值（曾经硬编码 20 秒）只会让列表在链路变慢时先于对话放弃，用户看到的症状是「对话能用，但刷新模型列表坏了」——指向 UI，而问题在链路上。同理，原始路径的每一条**降级**分支（JSON 解析失败、传输层失败、解析成功但没有 `data` 数组）都记 **Warning，并带上已读字节数与端点声明的 `Content-Length`**：三条都 `return null` 去走 SDK 回退，UI 上只剩回退那一轮的笼统失败，所以它们是「这次刷新为什么退化了」的唯一记录；而已读与声明的差额正是把「响应被截断」（2026-09-15 实测：完整 149 KB，只收到 3.8 KB / 7.6 KB / 30 KB / 31.5 KB，落的正是 JsonException 那一支）和「端点形状不认识」分开的那个数字，前者短读、后者读满。两者由 `TestModelCatalogTimeoutAndDegradationDiagnosticsAsync`（`Athena.Archive.Tests`）把住，其中超时那半用 `TaskCanceledException` 精确落到内部超时分支，所以断言不必真的等满一个窗口。

**推理档位只认 OpenRouter 记录里的 `reasoning.supported_efforts`。** OpenRouter 目录每个模型带一个 `reasoning` 对象（2026-10-19 实测：471 个模型里 337 个带，其中 204 个列出 `supported_efforts`，另有 `default_effort`），`ModelMetadataResolver.ReadReasoningEfforts` 从 `OpenRouterModelMetadata.Raw` 里读它进 `ResolvedModelMetadata.ReasoningEfforts`——快照本来就落了 `raw`，所以不改快照结构。`supported_parameters` 里的 `reasoning_effort` **不算佐证**：它只说收这个参数、不说收哪几档，而发一个模型不认的档位会被端点直接拒掉。不认识的档位名跳过，不猜。输入框底部模型名旁的推理强度按钮（`ReasoningEffortPickerViewModel`）只在这一项非空时出现，选项是「默认（目录的 `default_effort`）」加目录列出的档位；它写的是设置页里同一个 `ModelMetadataOverrides.ReasoningEffort`（按供应商 + 模型存，对用这个模型的所有会话生效，下一轮起作用），不是新设置。已经在设置页选了目录没列的档位时照实列出，不藏；没有佐证时选择命令拒写。`TestComposerReasoningEffortPicker`（headless）把住解析、三种目录形状、按钮的出现与消失、菜单项和写入。

**`top_provider` 的两个数都只对 OpenRouter 端点算数。** 窗口早就是这样（非 OpenRouter 端点用模型级 `context_length`），输出上限 `top_provider.max_completion_tokens` 曾经漏了这条，对任何匹配上的端点都生效，而它会经 `MaxOutputCeilingTokens` 变成第二轮起的 `max_output_tokens`。2026-10-19 TokenHub 的 `deepseek-v4.1-flash` 因此被许了 OpenRouter 主线路的 943718（同一模型的另两条 OpenRouter 线路是 393216 / 384000）；它的后端只收到 39 万左右，超过时按分到的机器间歇性回 `400001`「rejected by an internal MaaS component」——同一请求有时过、有时不过，第 2 轮过了第 3 轮挂（实测 ≤393216 二十四次全过，524288 与 943718 各六次四次 400）。现在非 OpenRouter 端点不借这个数：输出上限只来自用户覆盖或供应商自报，否则未知、请求退回保守的输出保留额。`TestProviderReportedMetadataLayerAsync`（`Athena.Archive.Tests`）把住两侧，撤掉修复时它失败。
