# OrcaRouter one-click sign-in

`Services/OrcaRouter/`: one-click OrcaRouter sign-in over PKCE (`OrcaRouterEndpoints`, `PkceCodes`, `LoopbackCallbackListener`, `OrcaRouterConnectService`, `OrcaRouterProviderBinder`).

The service only obtains a key — it does not know `AppConfig`, so a canceled flow cannot leave half a configuration behind; `OrcaRouterConnectViewModel` is the shared button state machine behind both entry points (the provider list's left rail and onboarding step 1), differing only in its apply callback. Endpoints and the referral code live in `Assets/Providers/orcarouter.json` rather than in C# constants, so changing the referral code is not a code change (and the open-source directory's review looks for `orcarouter` in a repository config file, which a README mention does not satisfy); the file is still not a steering wheel, because `Parse` enforces https plus a host allowlist, so editing the domain only makes the whole feature unavailable. The properties that are load-bearing, each of which has an assertion: the loopback end is a bare `TcpListener`, never `HttpListener` (which needs a URL ACL reservation on Windows and behaves inconsistently for non-elevated processes); a callback whose `state` does not match is logged and **ignored without ending the flow**, since ending it would hand any local process a switch for interrupting an authorization; a 2xx key exchange with no key field in the response is a failure, because writing an empty key produces a connection that reads as "connected" and 401s on every request; **failing to launch a browser is not a failure either** — the listener is still live, so the authorization URL is surfaced for the user to open by hand, and the manual path of pasting a key is never removed, because a loopback listener is exactly what corporate endpoint software blocks; one host gets exactly one connection (a second one would leave the roles pointing at the first, so the user sees "connected" and no change); and a role that already names a model is **never** repointed. The referral code appears only in the authorization URL's query and never in an API request. The flow is deliberately UI-only — it is not registered in `FunctionRegistry`, so no model can reach it.
