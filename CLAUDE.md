# CLAUDE.md - Athena.UI Project Context

This file serves as foundational guidance for AI interactions within the AthenaAgent workspace.

## 🚀 Project Overview

**Athena.UI** is a sophisticated, highly autonomous desktop AI assistant built with **.NET 10** and **Avalonia UI**. It is designed to be a "presence-like" intellectual partner with deep system integration capabilities, robust security, and a modern, polished interface.

### Core Technologi
- **Framework**: Avalonia UI 12.0 (Cross-platform XAML)
- **UI Themes**: `Semi.Avalonia` and `Irihi.Ursa.Themes.Semi` for a clean, modern aesthetic.
- **Runtime**: .NET 10
- **Architectural Pattern**: MVVM (using `CommunityToolkit.Mvvm`)
- **Dependency Injection**: `Microsoft.Extensions.DependencyInjection`
- **AI Integration**: OpenAI SDK 2.x (Chat, Embeddings, Image Generation, Tool Calling)
- **Markdown Rendering**: `LiveMarkdown.Avalonia` for streaming chat output with inline images, math, and native Mermaid diagrams (via `LiveMarkdown.Avalonia.Mermaid`, without JavaScript/WebView).
- **Browser Automation**: `Microsoft.Playwright` (Set-of-Marks visual grounding + vision-guided agent).
- **Audio**: no audio library. `SystemAudioService` shells out to the OS player (`afplay` / `powershell` / `mpg123`) through `ICliService`; there is deliberately no pause or seek. Do not reintroduce an audio component.
- **Logging**: Serilog with File and Console sinks.
- **Persistence**: JSON for config/history, Markdown for knowledge base, SQLite for vectors.

### Solution Layout
The repository is a multi-project solution (`Athena.UI.sln`):
- **Athena.UI** — the main desktop application (source lives at the repository root).
- **Athena.Updater** — standalone in-app updater executable (downloads/extracts GitHub releases; packaged alongside the app).
- **Athena.Archive.Tests** — test project covering conversation archive/history logic.
- **Athena.UI.HeadlessTests** — Avalonia headless UI assertion suite (see "Headless Tests" below).

Companion docs at the root: `AGENTS.md` (kept in sync with this file) and `README.md` / `README_CN.md`. Longer-form docs live in `Docs/` (user guides, `PrivacyPolicy.md`, `MinerU_API.md`, and `TechDebt.md` — known costs we have measured and deliberately not paid yet). Release tooling lives in `release.sh` and `Scripts/`.

### Key Features
- **Unified OpenAI-Compatible Model Roles**: One shared provider holds Base URL/API key data. Main conversation, title generation, context compression, automatic approval, embedding, browser, sub-agent, maintenance, and virtual-pet (`Companion`) roles independently select a model. The `Companion` role falls back to title generation when unset — both are one-line, low-latency, cheap calls, and a toy feature must not force another model assignment. TTS and image generation retain extension-specific connections.
- **Direct Tool Calling**: The main conversation directly owns built-in and MCP tool calls. Each call is one collapsed `ToolCallRowView` row (status icon + summary, details on click).
- **Bubble Rendering Budget**: `MessagesItemsControl` is a plain `ItemsControl` inside a `ScrollViewer` — **nothing is virtualized**, so every message of a session is realized at load and the whole tree stays live while scrolling. That makes the per-row control count the thing that decides whether a long conversation scrolls: a collapsed process row (`ToolCallRowView` / `ReasoningRowView`) must not build its detail subtree (`ToolCallEntry.ExpandedDetails` / `ChatMessageSegment.ExpandedReasoning` return null when collapsed), status/chevron icons are one `PathIcon` switched by key through `ToolIconKeyToGeometryConverter` (never several with `IsVisible`), segment kinds are picked by `ChatSegmentTemplateSelector` (not four parallel `ContentControl`s), and the shared row styles live in `App.axaml` rather than on each control instance. A 20-assistant-message stress conversation with 240 tool rows measured 14 039 visuals / ~6.6 s first layout before these cuts and ~10 300 / ~2–3 s after; `TestAssistantBubbleLayoutVisual` holds the per-row budget. Virtualization was considered and rejected — variable-height bubbles make the scrollbar jump.
- **Conversation Switch Veil**: Switching sessions in the left tree has no I/O to wait on — `InitializeConversationTreeAsync` restores every history into its own VM at startup — so the 2–3 s stall is entirely `MessagesItemsControl` realizing one conversation's whole bubble tree (see the rendering budget above). A veil cannot make that faster; it makes it legible. The switch runs in two beats and **the first beat does nothing but select**. `OnSelectedConversationChanged` flips `IsSelected`, raises `IsConversationSwitching`, and queues the outgoing session — that is all, because the row's own feedback is two UI-thread-clocked animations (`Border.row-accent`'s 0.38 s `scaleY` growth, the row background's 0.18 s fade) and they need an idle UI thread for their whole duration. Everything else was doing its work on top of those first frames, so the animation did not fail to play, it played in lurches: the empty-session sweep mutates the tree's `ObservableCollection`, the `MainConversationViewModel`/`DisplayedConversation` swap rebuilds the pet view and the whole bubble tree, `WorkspaceWorkbenchViewModel.SetWorkspaceAsync` disposes editor tabs and the file watcher and clears the file and Git collections, `TerminalPanelViewModel.ActivateScope` rebuilds the session list, and silent title generation samples messages on the UI thread. All of it now runs in `OnConversationSurfaceSwapDue`. The test for whether something belongs in beat one is narrow: is it "this row is now selected" itself? The gap between the beats is `ShellMaterial.RowSelectionSettle` (380 ms), which must equal the accent bar's transition duration — an assertion reads it off a realized row. It is a `DispatcherTimer` that **restarts on every selection change**, so walking the list with the arrow keys costs zero bubble-tree rebuilds until you stop, and the retirement queue is a list rather than one field because A→B→C has to settle both A and B. The veil lives **inside `MainConversationView`, in the message list's own `Grid.Row`** (driven by an `IsSwitching` styled property, same shape as `Workbench`), so it is exactly the size of the message area without the shell re-deriving "header is 40 px, the composer is this tall". Its content is the owl from the empty-conversation placeholder plus three pulsing dots, and **their motion is composition animation, never `Transitions` or `Style.Animations`** — this is the one place in the app where that distinction is load-bearing rather than an optimization. Avalonia's animation clock runs on the **UI thread**, which is frozen for the entire life of the veil, so a XAML keyframe animation would hold its first frame the whole time and a motionless "loading" reads as a hang. `ElementComposition.GetElementVisual(...).StartAnimation(...)` is evaluated by the render thread and keeps running through the freeze. An assertion walks the veil subtree and fails on any `Transitions`, because re-adding one is the natural-looking wrong fix. Three details are measured, not guessed: the owl's `CenterPoint` must be set to its midpoint or the breath scales about the top-left and reads as a twitch; every pulse animation's **first keyframe is its brightest end** and each dot's own `Opacity` stays 1, so a dead animation costs the motion and never the element (same rule as the workbench pane's entrance); and staggered dots need `AnimationDelayBehavior.SetInitialValueBeforeDelay`, since the default leaves the composition property at 0 until the delay expires — captured frames showed two of the three dots simply missing. `App.VeilAccentBrush` is far heavier than the hover overlays (0.32/0.38 vs 0.06/0.08) because an 8 px dot at hover-overlay strength disappears against the veil. `App.PanelVeilBrush` is **opaque** and does not follow the transparency slider: measured, both the slider-following composite (0.75 at panel 0.5) and a 0.97 fallback leave the outgoing conversation's body text legible, which cancels the veil's only purpose. It has a fallback definition in `Styles/Overlays.axaml` alongside the hover overlays, because the live brush is a **window-level** resource built by `ApplyShellPanelMaterial`; any other host (designer, a headless case's own `Window`) resolves nothing, `DynamicResource` neither throws nor warns, and the veil silently becomes a fully transparent no-op — rule 1's exact shape, and it happened here. Every path out of the swap lands in `EndConversationSurfaceSwap`; a stuck veil is the same silent failure. Switching also re-scrolls to the bottom from `MainConversationView.OnDataContextChanged`: a wholesale `ItemsSource` replacement raises no `Add` event and the attach handler ran long ago, so neither existing scroll trigger fires and the old offset just gets clamped into the new conversation (measured: 4391 of 4991). What none of this fixes is the freeze itself — the bubble tree is still one blocking layout pass, and the app ignores input for its duration; only incremental realization would change that, and it collides with the virtualization decision above. That is open tech debt, written up with its measurements, its blockers and the evidence that would settle it in `Docs/TechDebt.md`; read that before attempting it. `TestConversationSwitchVeil` and `TestConversationSwitchScrollsToBottom` hold the two beats, the settle wait, the coalescing, the retirement queue and the scroll; the shell case holds the veil's cell, clipping, opacity, the owl and dots, the no-UI-thread-animation rule, the reachability of the composition visuals and the accent-bar duration match.
- **Hover Costs Scroll Frames**: scrolling with the cursor over a bubble moves content under a stationary pointer, so `:pointerover` flips element by element and every flip pays for style re-evaluation and repaint. Two rules, both measured with `ATHENA_SCROLL_PERF=1 dotnet Athena.UI.HeadlessTests/bin/Debug/net10.0/Athena.UI.HeadlessTests.dll` (a per-pointer-move benchmark that is not part of the assertion run): **never animate a hover reveal inside the message list** — the 0.15 s opacity transition on `.bubble-actions` cost 16.9 ms per message-row crossing versus 1.1 ms without it — and **never style it through a cross-element descendant selector** (`Grid.message-row:pointerover StackPanel.bubble-actions`); bind a class instead (`Classes.hovered="{Binding $parent[Grid].IsPointerOver}"`). Process rows use `ProcessRowTheme` (App.axaml) rather than the Semi button theme for the same reason: fewer nested styles to re-evaluate per flip. Wheel handling over a heavy bubble went from 46.6 ms to 2.1 ms per event. `IsVisible` would be cheaper still than opacity, but it changes layout — one hover would relayout the whole list.
- **Interleaved Assistant Bubble**: An assistant message is an ordered `ChatMessage.Segments` list — `Markdown` / `Reasoning` / `ToolCallGroup` / `GeneratedImage` — appended in arrival order, so a bubble reads as "thought → called these → said this → thought again". Nothing is hoisted to the top of the bubble: reasoning is per-round (one segment per round, auto-expand follows `AutoExpandReasoning`, auto-collapses when the round ends), and a tool group is just "the calls of one round" with no group-level collapse. `ChatMessage.ReasoningContent` still holds the accumulated text, but only as the replay copy for context/compression; display comes from the segments. Legacy archives (message-level reasoning, no segments) are migrated on restore by `ConversationPersistenceHelper.PrepareRestoredMessage` — **it must materialize `Content` into a Markdown segment first**, because the moment a message has any segment, `UsesSegmentLayout` flips and the legacy Markdown renderer stops drawing `Content`. Two placement rules keep arrival order honest when a provider interleaves reasoning and text inside one round: **a reasoning delta that arrives after streamed body text must open a new segment** (`reasoningSealedByText`) instead of growing the segment above the text — otherwise "what it thought after writing that" is back-dated into the box above it; and because that puts a Reasoning segment last, `CommitActiveBubbleRound` decides whether to materialize `Content` from `_activeTextMaterialized`, **never from "is the last segment Markdown"**, which would append a second copy of the same paragraph.
- **Parallel Sub-Agents ("Owl Village")**: The `dispatch_subagents` tool fans out a batch of isolated sub-agents (presets: `general`, `researcher`, `file_worker`) with per-type tool gating, orchestrated by `Services/SubAgents/`. Progress is visualized as an owl-village overview (`OwlVillageView`) plus a side dock, with walk animations and batch curtain-call dismissal.
- **Knowledge Base (Vector Database)**: Local Markdown-based memory stored in `AthenaData/KnowledgeBase`. Powered by synchronous SQLite vector persistence to ensure 100% "what-you-write-is-what-you-search" real-time consistency. Retrieval is hybrid (L2-normalized vectors + BM25/FTS) with heading/path context and file-level result aggregation; the store carries an embedding-model fingerprint and supports schema migration.
- **Knowledge Base Self-Maintenance**: Write-time duplicate-detection guardrails on `create_new_memory`, plus a periodic maintenance agent (`KnowledgeBaseMaintenanceService` / `KnowledgeBaseMaintenanceRunner`) that consolidates and prunes memory files in the background.
- **Context Management**: Centralized `TokenService` provides UI-wide atomic tracking of context window pressure, with visual warnings as the threshold approaches; `ContextCompressionService` uses the independently configured compression role.
- **Image Generation**: OpenAI-backed image generation with logical continuity across turns; generated images render inline within Markdown chat output.
- **Audio Output**: speech is generated by the selected TTS provider (mp3 — providers reject wav) and played by `SystemAudioService` via the OS player; audio config is resolved per-model by `AudioConfigResolver`. Playback is fire-and-forget: no pause, no progress bar, because that would require an audio library back.
- **Browser Automation**: Vision-guided agent (`Services/Browser/`) using Playwright + Set-of-Marks annotation to plan and execute multi-step web tasks via the `run_browser_task` tool; its model is selected by the unified Browser Agent role. Three properties are load-bearing and easy to undo by accident: the agent **launches the machine's real Chrome/Edge first** (`RealBrowserChannels`) and only falls back to Playwright's bundled Chromium — the bundled one advertises `HeadlessChrome` and is what gets challenged by site protections; when it does fall back, the `HeadlessChrome` marker is stripped from the context user agent (UA Client Hints still leak it — turn off `Browser.Headless` if a site needs more). Screenshots go to the model at **`ChatImageDetailLevel.High`** with ~12px Set-of-Marks labels: `Low` squeezes the frame into 512px and the labels become unreadable, which makes the whole annotate/encode/store pipeline pointless. Label size is a two-sided constraint — under ~10px the number survives no downscale, over ~15px the number badge covers the neighbouring control it is supposed to help identify. The markup budget defaults to 150 elements (`Browser.SomMaxElements`, clamped 10–300) and a single task may override it through `run_browser_task`'s `somMaxElements`, since page density is something only the calling model can see. And `NetworkIdle` is awaited **only after a navigation**, never per observation — real sites never go idle, so a per-step wait burns its full timeout on every step.
  - **`input` types with real keystrokes** (`TryTypeWithRealKeystrokesAsync`), falling back to the JS value assignment in `FillEditableElementScript` only when the focused element does not hold the value afterwards. Assigning `.value` dispatches `input`/`change` but no key events, and autocomplete widgets — suggestion lists, station/city pickers, date panels — filter on `keydown`/`keyup` and write the site's hidden field only when an entry is committed. Without real keys the field *looks* right, the panel never narrows, the form submits empty, and the agent burns its whole step budget clicking an unfiltered panel (measured on 12306: 25 steps, ~10 min, no station ever selected). Verification reads `document.activeElement`, **not** the element under the click point — a suggestion panel covers the input, and a point hit-test would land on the panel and report "no editable target". `send_keys` key names go through `BrowserKeyNames.Normalize`, because the model writes `"ENTER"` and Playwright only accepts `"Enter"`.
  - **Stuck-state guard**: `ComputeStateSignature` hashes each observation (annotated screenshot bytes, or URL + DOM version + element values in DomOnly mode). At 3 identical observations the prompt gains a `<no_progress_warning>`; at 6 the task ends with a failure that names the loop. Actions that succeed while changing nothing keep `consecutiveFailures` at 0 forever, so before this the step ceiling was the only brake. `recent_actions_json` also carries each action's target/requested value — a history of bare `{"action":"input","success":true}` gives the model no way to see it is retyping the same value into the same box.
- **Document Parsing**: MinerU-based document parser (`Services/Parsers/`) exposed via `DocumentParserFunctions` (`get_document_outline`, `parse_office_document`) for extracting outlines/content from attachments (see `Docs/MinerU_API.md`).
- **Screenshot Capture**: In-app screenshot tool with option to hide or retain the window during capture.
- **In-App Updates**: `GitHubUpdateService` checks GitHub releases; the separate `Athena.Updater` performs the swap. Windows releases ship both a zip (for in-app updates) and a bilingual Inno Setup installer. (macOS DMGs are unsigned/ad-hoc signed — see project memory on Gatekeeper/App Translocation.) **One `osx-arm64` tar.gz serves both install shapes**, and it is the flat publish output, so it always carries `.playwright` at its root — which `ApplyUpdate` lands in `Contents/MacOS`, exactly where `release.sh`'s `create_app_bundle` refuses to keep it (codesign reads the driver's Mach-O `node` binary as a nested code object and rejects the whole bundle with "bundle format unrecognized"). `MacAppBundle.RelocatePlaywrightDriver` therefore moves it back under `Contents/Resources` after the swap, so an updated bundle has the same layout as a fresh DMG install instead of storing the 128 MB driver twice (measured on a real 1.6.6→1.8.2 install: 128M in each). Two alternatives were rejected with the reasons measured. **Deleting the `Contents/MacOS` copy instead of moving it is actively worse**: `Athena.UI/Program.cs` sets `PLAYWRIGHT_DRIVER_SEARCH_PATH` to `Resources` only when `Contents/MacOS` has no driver, so today the *fresh* copy is the one Playwright resolves (verified by invoking `Microsoft.Playwright.Helpers.Driver.GetExecutablePath` under both layouts) — deleting it would silently downgrade browser automation to the driver the DMG shipped. That same predicate is now also the fallback if a relocation ever fails, so **do not drop the `!Directory.Exists(baseDirectory/.playwright)` half of it**. And **the package cannot just omit the driver on macOS**, because the same archive installs flat tar.gz setups, which have nowhere else to get it. `AthenaData/Skills` is relocated by `create_app_bundle` too but needs nothing here — `AthenaData` is in `preservePaths`, so the symlink is never touched. The same pass writes the installed version into the bundle's `CFBundleVersion` / `CFBundleShortVersionString`, which `ApplyUpdate` otherwise never touches — the real install ran 1.8.2 while Finder and Gatekeeper still read 1.6.6. The version comes from the session's new `Version` field, falling back to the staged `Athena.UI.dll`'s `ProductVersion` (`StagedPayload.ResolveVersion`), and that fallback is not optional: **the session is written by the old installed app while the updater comes from the newly downloaded package**, so a new updater always meets sessions predating the field, and without it every existing install would stay stale one more release. The plist edit is a **targeted text replacement, never an `XDocument` round-trip** — `XmlWriter` re-emits the plist DOCTYPE with an empty internal subset (`...PropertyList-1.0.dtd"[]>`) and `plutil` rejects that outright ("unexpected character [ while parsing DTD"), so the tidier-looking version yields a bundle nothing on the system can parse. It writes through a temp file, because a half-written Info.plist is an app macOS refuses to launch at all. It must also stay **after** the relocation and **before** any future re-signing step: Info.plist is sealed into the signature. `TestUpdaterRestoresBundleDriverLayoutAsync` and `TestUpdaterRewritesBundleVersionAsync` (`Athena.Archive.Tests`, which compiles `MacAppBundle.cs` / `StagedPayload.cs` in by `<Compile Include>` — it has no `ProjectReference`) hold the layout, the idempotency, the flat-install no-op, the byte-for-byte plist fidelity, and the entry-name mapping (`Path.ChangeExtension` is wrong for the macOS entry: it reads `Athena.UI` as having extension `.UI`).
- **Mid-Stream Provider Failures**: `ChatFinishReason` is a **closed enum** in the OpenAI SDK — `ToChatFinishReason` throws `ArgumentOutOfRangeException` on anything but stop/length/tool_calls/content_filter/function_call, from inside `MoveNextAsync`, so the caller never sees that chunk (openai-dotnet#340 was closed as not planned; 2.13.0 still behaves this way). OpenRouter announces an upstream failure mid-stream with exactly that shape — `"finish_reason": "error"` plus a top-level `error` object — and it happened here on 2026-09-15: three turns died with the SDK's English assertion in the bubble while the real reason (`error.message`) was discarded with the chunk. `ProviderStreamSanitizer` (a `PipelinePosition.PerCall` policy on every `OpenAiClientOptionsFactory.Create` client) therefore rewrites unknown `finish_reason` values **in the SSE body**, before deserialization: the raw value moves to `athena_raw_finish_reason` on the choice, `finish_reason` becomes null, and the whole original chunk is logged once (`ProviderStreamUnknownFinishReason`) — that log line is the only place the upstream's own error text ever appears. `ChatCompletionsTransport` reads the moved value back out of `update.Patch` and throws `ProviderStreamInterruptedException`, which classifies as `ProviderErrorCategory.StreamInterrupted` and reaches the user as an explanation plus the provider's own words — keeping whatever text had already streamed. The SDK's retry policy cannot cover any of this: HTTP 200 is long past and the body is already flowing. **The rewrite must stay in the HTTP pipeline** — a `try/catch` around the enumerator (which the transport also keeps, as a second net) can only turn the throw into a better sentence, never recover the chunk. Held by `TestProviderStreamSanitizer` and `TestStreamedUnknownFinishReasonSurfacedAsync`; the latter's fixture is a reminder that an SSE event needs its trailing blank line or the parser drops it. A failure of this shape is also the one thing worth **resending**, and `ProviderRetryOptions` (Settings → Execution & concurrency → Provider requests; default on, 2 retries, 2s doubling, 30s per wait and 60s per round, ±20% jitter) is where that lives. Three rules make it safe rather than noisy. It sits **inside `ProcessStreamAsync`'s per-round loop**, where the request is byte-identical — tool results are appended only after a round succeeds — never at `StreamMessageAsync` level, which would rebuild the context, re-run compression and double-count anchors; a retry costs no tool round. It refuses to retry a round that has **already streamed answer text or a tool call**: those deltas are in the bubble and cannot be taken back, so resending would make the model write it all over again (reasoning-only rounds are fine — the view seals the interrupted segment and the next attempt starts a new one). And network failures only count as mid-stream **after the stream produced something**; a failure to connect is the SDK's own three retries, not this one's. A failure that surfaces after retries were spent is wrapped in `ProviderRetriesExhaustedException` purely to carry the count — every classifier, and the image-input fallback in particular, reads the inner exception, because turning that 400 into error text here is exactly what would silently disable the fallback. `TestProviderRetryPolicy` holds the backoff arithmetic and both caps; `TestProviderRetryResumesInterruptedStreamAsync` holds the recovery, the single announcement and the off switch; the no-retry-after-visible-output rule is asserted in `TestStreamedUnknownFinishReasonSurfacedAsync`.
- **Conversation Archive & Rewind/Fork**: Sessions are persisted and browsable; any turn can be rewound or forked into a branch session (fork markers live on the branch side, attachments are physically cloned, sessions support master/branch nesting). Archive logic is covered by `Athena.Archive.Tests`.
- **Cron Scheduled Tasks**: Standard five-field cron (`minute hour day-of-month month day-of-week`) is the only scheduling semantics; six-field expressions with seconds are rejected because `CronExecutionWorker` checks once per whole minute. `Services/Cron/` splits the concerns deliberately: `CronScheduleService` evaluates expressions (Cronos never leaks out of it), `CronTaskStore`/`CronTaskService` own persistence and the run state machine, `CronExecutionWorker` pumps due runs (concurrency fixed at 2, FIFO), and `CronSessionLauncher` turns a claimed run into a session. **Every firing opens a brand-new session and never changes `SelectedConversation`** — that is the whole design, and `MainWindowViewModel.AttachScheduledSessionAsync` must never touch the selection. DI runs one way only (`worker → task service + launcher`); the launcher's host and the task page's navigator are attached by the main window at runtime, which is what keeps the graph acyclic. Missed occurrences are fixed-policy **Skip**: however many were crossed while the app was closed, exactly one `Skipped` record is written and the next run is computed from now — never a backlog of sessions at startup. `RunOnce` disables the task the moment it is *claimed* (not when it succeeds), so a failure is not retried. **An API/provider failure is a failed run.** `OpenAIChatService` reports request-level failures as *text* (`[API 错误: …]`) rather than exceptions — the bubble reads better that way — so the stream ends normally and nothing throws. `GetAiResponseAsync` therefore only knew about failures that arrived as exceptions, and a real OpenRouter `response.failed` on 2026-09-13 was recorded as `succeeded` with a 「完成」 notification while the pipeline had stopped halfway. The signal is now explicit: `IChatService.StreamMessageAsync`'s `onProviderError` carries a `ChatTurnFailure`, and the provider's own message lands in the run record's `error`. Held by `TestProviderErrorFailsScheduledRun`. Model-behaviour endings (tool-round budget exhausted, an empty reply, a blocked tool call) are deliberately *not* failures — the API worked and 「继续」 resumes them. DST follows Cronos semantics, pinned by tests: a missing spring-forward time fires at the transition instant, an ambiguous fall-back time fires once for fixed-time expressions and twice for interval ones.
- **Virtual Pet ("Companion Loop")**: The window pet is an interaction surface, not just a status light. **Click = pat, and when a need is showing, that same click answers the need** — the cue glyph above its head is the instruction for what the click will do. Right-click opens the care menu (pat / feed / play / say something / profile / rest / hide), and **dropping files on the pet attaches them to the current conversation** through the same `AddStorageFilesAsync` path as the input box. There is deliberately **no double-click**: it would race the single click, and the pat has to be instant. Growth lives in `IVirtualPetProgressionService` (a singleton) rather than in the view model, because every session owns its own `VirtualPetViewModel` while the window shows exactly one pet — putting mood or level in the VM resets them on every session switch. Mood and energy are **advanced lazily from a timestamp**, never accumulated by a timer: with a timer, the eight hours the app spent closed simply never happen and the pet comes back exactly as tired as you left it. Cooldowns (pat 45 s, play 5 min, feed 15 min) **block the reward, not the feedback** — a cooled-down pat still animates and still says something, because a greyed-out button reads as "broken" and uncapped clicking makes the numbers meaningless. Needs (Hungry ≤ 30 energy / Bored ≤ 40 mood / Lonely after 45 idle minutes) are announced once and then live only in the cue glyph, and **the wrong interaction does not clear them**. Records are keyed by pet slug in `AthenaData/pet_profile.json`, so switching pets means meeting a new companion, not wiping the old one. Rules and every constant live in `VirtualPetProgressionRules`; `TestVirtualPetProgression` / `TestVirtualPetInteractionSurface` hold them. The profile panel is a `Popup` with `IsLightDismissEnabled`, and **the "档案" menu item must not open it from its `Command` — it opens from the context menu's `Closed` event** (`VirtualPetView.OnPetMenuClosed`). A window has exactly one `LightDismissOverlayLayer`, shared by the context menu and the panel: whoever closes hides it, no matter who else is still open. `MenuItem` raises `Click` *before* the menu closes, so opening the panel inside the command lets the menu's close switch off the overlay the panel just switched on — the panel renders fine but click-outside-to-close is dead, and only another window stealing focus (which deactivates the host and closes the popup) gets rid of it. `TestVirtualPetProfileDismiss` walks the real menu → click → outside-click path, because executing `ToggleProfileCommand` directly cannot reproduce it.
- **Pet Chatter**: Lines come from a local library first (`Pet.Line.<Topic>[.<MoodBand>]` in the locale files, `|`-separated variants so one scene costs one resource key) and are *optionally* replaced by a model line. The bubble always shows the local line **first**; a slow, throttled, unconfigured or failed model call is simply "not replaced", never a visible failure. `PetChatterService` throttles hard (45 s minimum interval, 20/hour, one in-flight, 8 s timeout) because a decorative widget must never generate open-ended API spend, and sends only the pet's own state plus the first 80 chars of the latest user input — never conversation history. Off by default (`VirtualPetChatterEnabled`). Two rules keep a model line from being silently thrown away, both of which "说句话" hit at once: **the bubble must not expire while a model line for it is in flight** — `BubbleDuration` is 4.5 s but a call may take the full 8 s `ModelTimeout`, so without `VirtualPetViewModel.ModelLineGrace` holding it open, only a model faster than 4.5 s could ever be seen; and **the 45 s minimum interval gates background chatter only** (`PetChatterRequest.UserRequested`), because automatic lines fire on every completed response and every accepted pat, so a shared interval means the one place the user explicitly asked for a line is the one most likely to lose it. The hourly cap still applies to everyone — that, not the interval, is the spend ceiling. `TestVirtualPetSpeakUsesModelLine` holds both, plus the bound that stops a hung request from pinning the bubble forever.
- **Panel Material & Shell Motion**: Every shell surface — the three `Border.shell-panel` panels, the utility/log panel, and the three workbench panels — takes its look from three window-level resources rebuilt in one place, `MainWindow.ApplyShellPanelMaterial` (formerly `ApplyShellPanelOpacity`): `App.PanelBackgroundBrush` (tint), `App.PanelBorderBrush` (rim), `App.PanelShadow`. **A new panel gets the material for free by consuming those three keys** — do not add a class toggle or a per-view binding. `MainLayout.PanelGlassEnabled` switches the frosted-glass material on; it is orthogonal to the `PanelTransparency` slider, except that glass **clamps the tint to `ShellMaterial.GlassTintOpacity`** — with the slider at 0 the panel is fully opaque and would hide the glass entirely, so the toggle would silently do nothing. The blur is a **second copy of the background image decoded to 96px and upscaled by `UniformToFill` with `HighQuality` interpolation**, not `Effect="blur(n)"`: the effect is a full-window offscreen pass every frame and the image is static, so the upscale buys a smooth blur for zero runtime cost. The tint ceiling is **theme-dependent and that asymmetry is not a taste call**: `GlassTintOpacityLight` (0.80) must stay above `GlassTintOpacityDark` (0.62), because light-theme body text is dark ink on a pale ground, so backdrop luminance variance eats its contrast directly — 0.62 rendered the session tree unreadable in light and perfectly fine in dark (confirmed from captured frames). An assertion holds the ordering. The remaining opacity/alpha values are **starting values, not measurements**, and are there to be eyeballed across both variants and all five color schemes. Window-level acrylic (`ExperimentalAcrylicBorder` / `TransparencyLevelHint`) is not an option here — it blurs the *desktop* behind the window, not the app's own background image, and it collides with `ExtendClientAreaToDecorationsHint` (AvaloniaUI/Avalonia#21082). The 260 ms crossfade is a declarative `DoubleTransition` on the two backdrop layers, deliberately **not** a hand-written `Animation.RunAsync`: the imperative version needs the "pre-set the local value to the animation's end value" dance to avoid a final-frame jump, plus a guard against a fast off→on toggle whose first fade-out erases the second fade-in. Because a transition shadows the property getter mid-ramp while the headless render timer never ticks on its own, assertions read `GetBaseValue(Visual.OpacityProperty)`, never `Opacity`. Shell micro-interactions all live in `MainWindow.axaml`'s `Window.Styles` and **none of them reach `MainConversationView`** — see the hover/scroll measurements above. Hover and press feedback runs off three brushes — `App.HoverOverlayFaded` / `App.HoverOverlay` / `App.PressOverlay` — which are **one color differing only in `Opacity`** (white on dark, black on light). They live in `Styles/Overlays.axaml`, an application-level **merged** dictionary, and that placement is load-bearing: `App.SetColorScheme` assigns `app.Resources.ThemeDictionaries[Dark]`/`[Light]` **wholesale**, so a key defined only in `App.axaml`'s theme dictionaries vanishes the moment a user picks Solarized/Cyberpunk/Tokyo/Monokai — which is exactly why those eight scheme files are 136-line full copies. A merged dictionary is outside that replacement, so the overlays are defined once and survive every scheme. An assertion switches to a non-Default scheme and re-resolves them. They are static theme-variant data, so they are **not** rebuilt by `ApplyShellPanelMaterial`. That is not a style choice: a `BrushTransition` must never start from `Transparent`, because straight-alpha interpolation passes through translucent white and flashes on dark themes (AvaloniaUI/Avalonia#15419); `Transparent` is `#00FFFFFF`, so the fix is a same-hue zero-alpha brush. `App.SelectedBackgroundFaded` is the same trick for the row-selection fade. **`Window.Styles` outranks the Semi `ControlTheme`**, so `Button.icon-plain`'s `Background="Transparent"` silently shadowed Semi's own `:pointerover` background — every icon button in the shell had no hover feedback at all until an explicit `:pointerover` rule was added. Anything that pins `Background` in `Window.Styles` owes its own hover rule. Buttons that sit inside scrollable lists (`icon-plain`, `session-row`) get a brush fade only; transforms (hover lift, press compress) are reserved for fixed-position buttons (`launcher`, `titlebar-action`). The conversation row's selection accent is a 3px `Border.row-accent` scaled on `scaleY` over 0.38 s — a compositor transform, so it never relayouts the tree — and it binds `Classes.on` straight to `IsSelected` rather than using a `Grid.conversation-row.selected Border` descendant selector, per the same rule that governs `.bubble-actions`. The bar sits at the row's left edge, so the gap between it and the conversation icon is **`Button.session-row`'s left padding**, not a margin on the bar; padding the bar would only make the bar itself thinner. The workbench pane's entrance is a one-shot `Style.Animations` on a `.shown` class, deliberately **not** "base `Opacity=0`, `.shown` sets 1": with the latter a broken class binding leaves a permanently invisible pane, which is rule 1's silent failure. Here the local value is always fully visible and the animation merely plays once when the class attaches, so a missing class costs the animation, never the panel. The utility panel's log/terminal cross-fade could not take that shape. Avalonia's `TabControl` has no transition property, and although its single content host really does detach the old page and attach the new one (`DetachedFromVisualTree`/`AttachedToVisualTree` each fire once, measured), **`Style.Animations` does not replay on re-attach** — the page reads `Opacity` 1.000 the instant it comes back, so a purely declarative fade is not merely subtle, it never runs. `MainWindow.OnUtilityTabSelectionChanged` drives it instead, and it **must start the animation synchronously — never `Dispatcher.Post` first**. An earlier version deferred a beat, on the untested assumption that the new page was not realized yet at `SelectionChanged` time; it is (measured: the incoming page is already in the visual tree when the event fires). The deferral produced a visible double flash — content appears at full opacity, blinks out, then fades in — because the extra dispatcher turn contains a paint. Measured timeline for the synchronous version: opacity is still `1.000` the instant the setter returns, but `0.000` after **one dispatcher turn, before any render frame**, so nothing ever paints unfaded. Note the limit of the guard here: the headless suite **cannot** catch a re-introduced `Post`, because `RunJobs()` drains the queue without rendering, so both shapes look identical to it. `SettleUtilityTabFade` asserts the fade runs at all and completes; only the code comment protects against deferring it again. The fade is **opacity only, and the terminal page opts out of it entirely**. A 6px rise was tried and reverted: giving a control that has no `RenderTransform` one makes it re-rasterize its glyphs at fractional offsets when the transform appears and snap back to integer positions when it is removed, and on the terminal's monospace grid those two re-rasterizations read as a visible twitch at each end of the animation. Two terminal-specific explanations were measured and ruled out first, so neither is worth re-investigating: `TerminalPanelView.OnAttachedToVisualTree` calls `RecreateTerminalControl` on every attach, but its guard holds and the same `TerminalControl` instance survives repeated tab round-trips; and the terminal's bounds do **not** collapse while the tab is hidden, so there is no PTY reflow on return. The terminal therefore carries no `utility-tab-page` class at all — a live glyph grid is the wrong place for an entrance animation, and its whole value is being readable instantly. An assertion holds that deliberate absence, because "add it back for consistency" is the obvious wrong fix.
That leaves a trap worth naming, because it applies to every entrance animation here: **a running animation shadows the property getter, and the headless render timer never ticks on its own**, so an animation started in a test stays near its first keyframe for the rest of the run — a faded tab page would silently dim every frame captured afterwards. The fix is `AvaloniaHeadlessPlatform.ForceRenderTimerTick()` inside a `PumpUntil` predicate, which both advances the clock and asserts the animation completes; `SettleUtilityTabFade` does exactly that and is why `main-window.png` is still captured at full brightness. Where an animation is not driven that way, read `GetBaseValue` rather than the property. The overlay-brushes-share-one-color invariant, the "a hovered button actually gets a background" regression, and the accent bar's two states are all asserted in the headless shell case. Constants and the clamp rule live in `ShellMaterial`; the headless shell case (the one printing `[PASS] three semantic columns, utility tabs, side minimum widths, permanent chat, panel material ..., and shell micro-interactions`) asserts every one of them, on and off.
- **OrcaRouter One-Click Sign-In**: "Connect with OrcaRouter" appears in onboarding step 1 and above the provider list; a PKCE browser authorization writes the API key into a provider connection without the user ever copying one. Typing a Base URL and key by hand is still a first-class path and must stay — a loopback listener is exactly the thing corporate endpoint software blocks. See `Services/OrcaRouter/` in the directory map for the rules that hold it together.
- **Multi-lingual**: Full runtime localization support (English, Chinese) via `AssetLoader` stream parsing.

## 🛠️ Building and Running

Ensure you have the .NET 10 SDK installed.

| Action | Command |
|--------|---------|
| **Restore** | `dotnet restore` |
| **Build** | `dotnet build` |
| **Run** | `dotnet run` |
| **Release** | `dotnet build -c Release` |
| **Headless Tests** | `Scripts/run-headless-tests.ps1` (PowerShell) or `Scripts/run-headless-tests.sh` (Git Bash/CI) |

### Claude Code on the web (`.claude/hooks/session-start.sh`)

Remote sessions start without a .NET SDK. The SessionStart hook installs
`dotnet-sdk-10.0` **from the Ubuntu archive** (`noble-updates/main`) and warms the
NuGet cache with a solution restore; it is a no-op on a local machine (`CLAUDE_CODE_REMOTE`).
Two things about it are load-bearing:

- **Do not switch it to `dotnet-install.sh`.** `dot.net/v1/dotnet-install.sh` redirects to
  `builds.dotnet.microsoft.com`, which — along with `aka.ms`,
  `download.visualstudio.microsoft.com` and `dotnetcli.azureedge.net` — answers 403 to CONNECT
  under the session's egress policy. `archive.ubuntu.com` over port 80 is reachable directly.
- **`apt-get update`'s exit code is not a gate.** The container ships deadsnakes/ondrej PPA
  sources that are 403 under the same policy, and apt downgrades a single failed source to a
  warning and still returns 0 — so the code proves neither success nor failure. The real gate is
  the `install` plus the `dotnet --list-sdks` recheck after it.

Also: the remote agent runs as **root**, and root bypasses DAC permission checks
(`CAP_DAC_OVERRIDE`). Two `Athena.Archive.Tests` cases chmod a directory to `0500` and assert the
write is refused, which cannot hold as root — they are guarded by
`ReadOnlyDirectoryBlocksWrites()`, which probes the capability instead of inferring it from the
uid, so the assertions still run (and still fail) anywhere they are meaningful.

### Headless Tests (`Athena.UI.HeadlessTests`)

Avalonia headless assertion suite — a console program with 60+ sequential cases (~2 min total). Assertion messages are written in zh-CN because the harness pins the zh-CN culture at startup.

- **Always run via `Scripts/run-headless-tests.ps1` / `.sh`, never `dotnet run`**: `dotnet run` rebuilds the whole solution, and a running Athena.UI instance locks `bin\Debug\net10.0\Athena.UI.exe`, failing the build (MSB3027). The scripts build with `-p:UseAppHost=false` (DLL only) and execute the suite DLL directly.
- **Exit code is meaningful**: the suite ends with `Environment.Exit(exitCode)` (headless Avalonia never shuts down on its own and the process would otherwise hang forever). All passing prints `[ALL HEADLESS TESTS PASSED]` and exits 0 — CI-able.
- **Never poll with `await Task.Delay` + `RunJobs` on the main thread**: the await continuation is posted to the dispatcher queue, and `RunJobs()` only runs after the await → deadlock. Use the `PumpUntil(done, timeoutMs, failureMessage)` helper for any condition waiting. The workbench tests still contain legacy `await Task.Delay` polling that happens to pass because their timers pump the dispatcher — **do not copy that pattern into new tests**.
- **`SwitchLanguage` is global, so a test that switches languages must switch back.** `LocalizationService.SwitchLanguage` swaps the *application's* resource dictionaries, not just that instance's, so a case that loops over `["zh-CN", "en-US"]` and stops on English leaves every later UI assertion reading English while the suite asserts zh-CN. That is not a clean failure: the shell test's menu poll never matches, falls into the `await Task.Delay` path above, and the whole run **hangs with no message** instead of failing. End any language-looping case with `SwitchLanguage("zh-CN")`.
- **Iterate with a minimal repro first**: cases run sequentially in file order, so a test inserted mid-file takes ~100 s per full-suite iteration to reach. Validate new logic in isolation (construct VM + stub directly) before merging into the suite.
- Redirect output to a file and tail it — piping to `tail` block-buffers and hides live progress.

Prefer it over listing a tree and searching file by file.
    - `KnowledgeBaseFunctions`: Semantic memory management (`create_new_memory`, `recall_from_memory`).
    - `WebSearchFunctions`: Real-time web information retrieval.
    - `CliFunctions`: Execution of safe terminal commands.

Schedules are cron expressions only — the old natural-language time parsing ("in 2 hours", "明天下午") is gone, and every failure returns structured validation so the model can correct itself instead of retrying the same bad input.

Cross-run find/replace lives in `RunTextEditor`; styles and numbering in `DocxStyleLibrary`; `WordprocessingSchema` holds the ordered content models — always add property elements through `SetProperty`, since out-of-order children are what make Word offer to "repair" a file. The `docx` built-in skill only supplies routing and workflow discipline.

The service only obtains a key — it does not know `AppConfig`, so a canceled flow cannot leave half a configuration behind; `OrcaRouterConnectViewModel` is the shared button state machine behind both entry points (the provider list's left rail and onboarding step 1), differing only in its apply callback. The properties that are load-bearing, each of which has an assertion: the loopback end is a bare `TcpListener`, never `HttpListener` (which needs a URL ACL reservation on Windows and behaves inconsistently for non-elevated processes); a callback whose `state` does not match is logged and **ignored without ending the flow**, since ending it would hand any local process a switch for interrupting an authorization; a 2xx key exchange with no key field in the response is a failure, because writing an empty key produces a connection that reads as "connected" and 401s on every request; **failing to launch a browser is not a failure either** — the listener is still live, so the authorization URL is surfaced for the user to open by hand, and the manual path of pasting a key is never removed, because a loopback listener is exactly what corporate endpoint software blocks; one host gets exactly one connection (a second one would leave the roles pointing at the first, so the user sees "connected" and no change); and a role that already names a model is **never** repointed. ### Coding Conventions
- **MVVM**: Strictly separate UI (`Views`) from logic (`ViewModels`).
- **DI**: Register all services in `App.axaml.cs`. Inject via constructor.
- **State Synchronization**: Avoid local state duplication. Use singleton services (like `ITokenService`) and bind `ViewModel` properties directly to these services.
- **Async/Await**: Use asynchronous patterns for I/O and AI calls. Avoid `Task.Run` for critical data persistence (like Vector indexing) to prevent race conditions.
- **Logging**: Use `Serilog` via constructor-injected `ILogger` or global `Log` class (File + Console sinks).
- **Attributes**:
  - `[ObservableProperty]`: For bindable fields in ViewModels. Ensure properties use PascalCase in bindings.
  - `[NotifyCanExecuteChangedFor]`: Apply to state variables (like `_isSending`) to automatically re-evaluate command availability.
  - `[RelayCommand]`: For command methods.
- **Localization**: Use `{loc:Loc KeyName}` in AXAML for translatable strings.

### Review Rules — what "good" means in this repo

Ordered by **when the mistake surfaces**, not by how bad it feels. Silent failures come first because nothing else will ever report them. A rule earns its place only if it names a measured cost or a failure that actually happened here.

1. **A missing dependency must fail loudly, never degrade silently.** Constructor parameters that the production path requires are non-nullable; if a service is genuinely optional, the null branch must log. `Foo?` + `_foo?.Bar()` everywhere means a mis-wired composition root shows up as "the button does nothing" months later. Designer/test construction goes through an explicit `CreateForDesigner()`-style factory, never through a parameterless constructor that passes nulls for everything.
2. **Persistence is a whitelist, not whatever the type happens to expose.** `ChatMessage`, `ChatMessageSegment`, `ToolCallEntry` and `ChatAttachment` are simultaneously render models and the on-disk archive schema, so **every** computed property, transient UI flag, and `[RelayCommand]`-generated property must carry `[JsonIgnore]` / `[property: JsonIgnore]`. The authoritative definition of "persistent" is *what `ConversationPersistenceHelper.CloneMessage` copies*; anything it refuses to copy, and anything `PrepareRestoredMessage` resets, does not go to disk. This is enforced by `TestPersistedMessageFieldWhitelist` in `Athena.Archive.Tests` — when it fails, add `[JsonIgnore]`, do not extend the whitelist unless the field is genuinely restored. Measured before the guard existed: `ChatMessage` wrote 51 fields per message where 17 are actually restored; re-serializing the real 24-conversation / 794-message archive under the whitelist cut it from 6 589 718 to 4 067 605 bytes — **38.3 % of the archive was write-only state** (the store uses `WriteIndented = true`, so each junk field costs its own line). The derived properties duplicated `content` into `displayText` and the entire attachment array into `attachmentPanelItems`, and — because `ConversationArchiveStore` skips a write when `payload_hash` is unchanged — transient flags like `isLoading` flipping mid-stream defeated that write-skip and forced full-payload rewrites. Only the two properties that would have *crashed* the serializer (`LegacyMarkdownContent => this` recursing, `SegmentContent`) had ever been noticed; the other 25 failed silently for their whole lifetime. That asymmetry is the rule's whole point.
3. **Never block a thread waiting on the dispatcher.** No `Dispatcher.UIThread.InvokeAsync(...).GetAwaiter().GetResult()` / `.Result` / `.Wait()`, on either side. Make the method `async` and `await` it; if a synchronous entry point is unavoidable, marshal with `Post` and return without waiting. The app already burned itself on this once — see the comment on `MainWindowViewModel.PersistSessionStateAsync`, where the old blocking implementation deadlocked shutdown into a force-kill. **When you fix one instance of a hazard, sweep for the rest of them in the same commit**; that deadlock was fixed in one place and left standing in another for months.
4. **A service-layer signature may not name a ViewModel or an Avalonia type.** Look at the *signature*, not the `using`: `Services/Platform/*` are legitimate host adapters and may reference Avalonia inside their bodies. But an abstraction whose members are typed on a ViewModel — as `ISubAgentOrchestrator.ActiveAgents` once was (`ObservableCollection<SubAgentViewModel>`) — can never have a non-UI implementation, which cancels the decoupling at the point of declaration. Services expose domain state (`IReadOnlyList<SubAgentSnapshot>` + a change event); the ViewModel layer does the projection. `Services/Cron/` is the reference shape.
5. **`async void` is for real event handlers only, and the body is wrapped in `try/catch` that logs.** A timer callback or a `Task`-returning path that is `async void` turns any exception into an unhandled process-level crash. Prefer `async Task` awaited by the caller.
6. **An empty `catch` must name what it swallows and why it is safe.** `catch { }` with no comment is indistinguishable from a bug. If the answer is "this can't happen", log at debug and move on.
7. **A new invariant ships as an assertion, not as a comment.** Comments do not survive the next refactor; `Athena.Archive.Tests` / `Athena.UI.HeadlessTests` cases do. This is why rule 2 has a test and not a paragraph.
8. **Docs here are load-bearing spec.** `CLAUDE.md` / `AGENTS.md` are the only entry point an agent gets, so a stale claim produces wrong code directly. Deleting a component means editing every doc that claims it exists — the audio stack was replaced but both docs still advertised `LibVLCSharp`, and `AGENTS.md` pointed at a `CONTEXT.md` that had been deleted.
9. **Size is not the criterion; net direction is.** `MainConversationViewModel` is ~4 600 lines and that alone is not a finding. Ask whether the change *moves responsibility out* (as `ConversationExecutionCoordinator` and the `ICompression*` split did) or *deposits more in*. Do not split a class to hit a line count — it produces incohesive partials and fixes nothing.
10. **Do not relitigate decisions that already have measurements.** Message-list virtualization, the `.bubble-actions` hover transition, `ProcessRowTheme`, `ChatImageDetailLevel.High`, and the 5-field cron restriction were all decided against alternatives with recorded numbers. Overturning one requires better numbers, not a tidier-looking diff.

### Function Discovery Rules
When adding new tools:
1. Implement the logic in a class under `Services/Functions/`.
2. Register the tool in `FunctionRegistry.cs` with a clear description and JSON schema. **Descriptions must guide the AI clearly** (e.g., advising on when to use `write_system_file` vs `modify_system_file`).
3. If the tool modifies the Knowledge Base, it MUST trigger `RefreshVectorCacheAsync` to keep the vector database aligned with the file system.

## 🛡️ Operational Integrity & Security
- **Tool-Use Approval Gate**: A code-level approval chokepoint lives in `FunctionRegistry.ExecuteAsync`, so all three tool-execution paths (main chat, parallel sub-agents, KB maintenance) funnel through it and cannot bypass it. `ToolRiskClassifier` tiers every tool (ReadOnly / AdditiveWrite / Sensitive / Destructive), with `TerminalCommandRisk` doing command-level evaluation of `execute_terminal_command` (catches `bash -c "rm -rf"`, `curl|sh`, `sudo`, `chmod 777`, etc., and unwraps `shell -c "<payload>"` so wrapping cannot downgrade a destructive command). **AdditiveWrite** covers calls that can only create a new file and structurally cannot overwrite or delete (Office create/edit/convert with `overwrite` unset, `create_directory`); they auto-allow in Balanced and still prompt in Strict, and `overwrite=true` escalates them back to Sensitive. `ToolApprovalKey` scopes the dedup key so "always allow" is never blanket: terminal by command name, `fetch_url_to_file` by host, file writes by target directory (pre-existing unscoped entries keep working). `ToolRiskClassifier.IsNeverUnattended` blocks `modify_self_configuration` and MCP server management on unattended paths regardless of `SubAgentsInheritApproval` — otherwise a sub-agent could write `Security.ToolApprovalMode = Off` and disable the gate itself. `ToolApprovalContext` (AsyncLocal) selects the execution mode — Interactive (main chat → `ToolApprovalDialog` popup), NonInteractive (sub-agents → static policy: destructive always denied, sensitive gated by `SubAgentsInheritApproval`), Trusted (KB maintenance auto-allow), or Unset (fail-safe deny). `ToolApprovalService` owns the policy + Serilog audit; behavior is configurable via `ToolApprovalMode` (Off/Balanced/Strict, default Balanced), `AutoAllowedTools`, and `TerminalAllowlist` in the "Tools & Security" settings section. See `Docs/ToolApproval_Implementation_CN.md`.
- **System Notifications**: `ISystemNotificationService` (`Services/Notifications/`) fires on three events, each next to the existing `App.StartTrayFlashing()` call: a tool approval arriving (`ApprovalQueueViewModel` — the only `Critical` one, because an unanswered approval stalls the whole turn until it times out), a reply finishing (`MainConversationViewModel.NotifyAssistantReplied`), and a cron run finishing (`MainWindowViewModel.NotifyScheduledRunCompleted`, keeping the existing `isFailure || notifyOnCompletion` policy — a silently failing scheduled task is no scheduled task). **A scheduled run flows through the reply-end code too**, so `NotifyAssistantReplied` bails on `IsScheduledRun`; without that guard one cron trigger fires two toasts, and the cron one is strictly better (it knows the task name and the outcome). Keys are per-conversation (`athena.reply:<id>`, `athena.cron:<id>`) so two sessions finishing never overwrite each other, while the approval queue deliberately shares one key — its requests all collapse into one window anyway. It is deliberately narrow: **no click callbacks**, because Windows unpackaged apps need a COM activator for those and `osascript`/`notify-send` cannot deliver them at all — a notification's job is to bring the user back, and the session tree's own unread markers (`HasUnreadCompletion` / `ScheduledRunFailed`) are how they find the spot. `IAppForegroundProbe` must be read **before** `EnsureWindow()` (which activates the window, making "is anyone watching" answer yes forever), and it checks *every* window, not `MainWindow` — the approval queue is its own window, so a MainWindow-only check reads "user absent" while they are staring at the prompt. Three platform facts are measured, not assumed: an **unregistered Windows AUMID makes `Show()` a silent no-op** (no exception — so a try/catch fallback never fires). Toast identity on unpackaged Win32 comes from a Start Menu shortcut's `System.AppUserModel.ID`, not from the process, so `WindowsShortcutAumid` stamps that property via `IShellLink` + `IPropertyStore` on a one-shot STA thread — there is no CLI substitute, `Shell.Application` cannot write the property store. It **patches an existing shortcut rather than rebuilding it** (the installer's copy carries icon and working directory worth keeping), **never overwrites an AUMID already present** (that is the identity earlier notifications were filed under), and only reads the all-users copy since a per-user install cannot write `ProgramData`. `Scripts/windows-installer.iss` stamps the same `AppUserModelID` for fresh installs; without either, notifications fall back to PowerShell's own AUMID and are signed "Windows PowerShell". the toast script must go through **`-EncodedCommand`**, because the `template="ToastGeneric"` quotes get eaten in command-line re-parsing and `LoadXml` fails with `0xC00CE502`; and Windows PowerShell 5.1 is required (`pwsh` cannot load WinRT types). Linux prefers `gdbus` over `notify-send` — glib is present wherever a notification daemon is, libnotify-bin often is not, and only gdbus returns the id that replace/withdraw need. macOS is stuck on `osascript` until `release.sh` does more than ad-hoc signing, so it has no urgency and no withdraw. The escaping for all three parsers is pinned by `TestNotificationPayloadEncoding`; the three trigger policies by `TestApprovalNotificationWiring`, `TestReplyFinishedNotification`, and the cron host block's `ReportOutcome` assertions. Only the Windows backend has been exercised against a real desktop — the Linux and macOS command shapes rest on those escaping assertions alone.
- **Data Sandbox (`AthenaData`)**: All application state (config, logs, history, knowledge base) is strongly sandboxed within the `AthenaData/` folder located in the application's base directory.
- **System File Protection**: `FileSystemService` enforces strict security boundaries:
  - **Blacklists**: Hard blocks on critical paths (`/etc`, `/sys`, `C:\Windows`) and risky extensions (`.exe`, `.dll`, `.sys`).
  - **Self-Preservation**: AI tools are structurally prohibited from modifying the application's own `config.json` file.
  - **Quotas**: Limits on read/write sizes per operation to prevent memory exhaustion or disk flooding.
- **Tool Result Budget**: `FunctionRegistry.ExecuteAsync` is also the single chokepoint for result size (`Security.MaxToolResultChars`, default 60 000 chars). Oversized results are compressed by `ToolResultTruncator` — long array tails dropped first, then long text water-filled so short metadata (paths, paging cursors) always survives — and flagged with a `truncationNote`. Before this, only `execute_terminal_command` capped its output; `parse_office_document` in particular could return a whole book inline (it now takes an `outputPath` to write Markdown to disk and return only a heading map).
- **The tool list is a per-turn snapshot**: `CreateRequestRuntimeSnapshotAsync` builds `EffectiveRequestRuntimeSnapshot` (including `options.Tools`) **once per user turn**; the agentic loop in `ProcessStreamAsync` reuses it for every round. **A model therefore cannot acquire a tool mid-turn.** Any "call this tool to unlock more tools" design is broken here: the flag flips but nothing re-reads it, so the model is told a tool exists, never sees it, and burns the whole iteration budget calling a name the provider degrades to the nearest real tool. Whether Office tools ship is decided at snapshot time by `OfficeToolRelevance.IsRelevant(context)` — a pure function over the conversation, deliberately biased toward including them (a false positive costs tokens; a false negative breaks the task). `Extensions.OfficeToolsMode` = Auto/Always/Off. Keep `GetToolDeclarationTokenCount(includeOfficeTools)` fed by the same predicate or the context meter reports declarations that were never sent.
- **Runaway-Retry Guard**: `RepeatedToolFailureGuard` refuses a tool call after it has failed 3 times with byte-identical arguments, returning a result that names the dead end and lists the ways out. The iteration ceiling only guarantees the loop *eventually* stops; this stops it immediately. Tools must also be **idempotent where their postcondition allows it** — `create_directory` reports success on an existing directory (`mkdir -p` semantics, with a `created` flag), because reporting "already exists" as a failure gives the model nothing to change and is exactly what triggers a retry loop.
- **Parallel Tool Calls**: `ToolCallParallelism` batches a turn's tool calls (`Security.MaxParallelToolCalls`, default 4). Only *consecutive* read-only calls are batched — never reordered across a write — and only under Off/Balanced approval, where read-only calls provably never prompt. `run_browser_task` is the one non-read-only exception, batched under Off only (where nothing prompts): each task owns an isolated `BrowserContext` and the time is nearly all network and model waiting. For the same reason there is no longer a browser gate in `SubAgentToolGates` — the browser process is shared but its contexts are not, and `EnsureBrowserAsync` refuses to restart the process while sessions are live, which was the only real hazard. Results are always written back in the original order to satisfy the `tool_calls` pairing constraint. Set 1 to restore strictly sequential execution.
- **Tool Transparency & Lifecycle**: Tool executions provide visual feedback ("正在调用: xxx...") while executing, transitioning to ("xxx 调用完毕，持续思考中...") during subsequent network waits. Intermediate JSON tool-call messages are kept in context but hidden from the UI to avoid clutter.
